# 迁移阶段与验收门槛

所有阶段当前均为 **planned**。这里的编号表示依赖和能力出口，不是已完成进度。细分任务见 [任务清单](tasks.md)，接口定义见 [架构](architecture.md)，执行证据格式和比较规则见 [验证协议](validation.md)。

## 全程不变的约束

- 生产路径是自有语义系统、SoN、native 后端与构建流水线，正式目标对象不用 LLVM/Cranelift 生成。
- 参考 rustc 的成熟实现和回归用例，统一到自己的数据模型；不以完整复制 rustc 再包一层接口作为完成迁移。
- 保留有限、明确的能力范围；超出范围时给出诊断，不能生成不可信的对象或静默选择另一个后端。
- 原始目标保留：相同语义、features、target 和产品配置下，真实项目体积与 runtime 不退化，编译时间改善。开发期的性能退化可以记录为待解决差距，不能当成最终验收通过。
- move、借用、drop、布局与内存效果是语义要求，不用“支持语法”替代。`panic=abort` 或禁用 SIMD 等缩减不能未经声明改变比较条件。

## M0：版本、语义范围与基线

**输入：** 当前 clean commit、已知错编译样例、候选 rustc 源码版本及固定的目标项目。

**工作：** 保存源码/工具链/产物指纹；确定初始 Linux x86_64 目标、edition 和能力范围；固定官方 rustc 参考 commit 与对照二进制；建立正例、拒绝例、真实执行和诊断分类的 harness；确认已发现错误属于哪些路径。

**出口：** 从干净输入可以复现错误；一个最小成功用例和一个预期拒绝用例具有完整记录；原始二进制与重新构建结果不混淆；基线耗时和机器来源可追溯。正式参考版本尚未固定时不能开始依赖具体内部契约的大规模移植。

**继续决策：** 选择满足真实依赖图需求的参考版本；写明本地派生 rustc 快照与官方源码的区别。M0 完成只证明实验基础可用，不证明任何新语言能力。

## M1：贯通自有生产链

**依赖：** M0；共享 ID、类型、Typed Body 和效果契约可用。

**工作：** 适配成熟词法/语法算法到 AST，完成函数和简单模块的名字/类型检查，生成 Typed Body，经控制流/变量状态构造 SoN，复用已验证的机器码基础；生产入口与旧 `.kfr` 测试入口显式分开。

**出口：** 一组普通 Rust 文件和简单多模块程序完整经过新链；分支、循环、赋值、递归调用及边界整数差分通过；原有 if 表达式错编译类有真实机器回归；无效用例被拒绝。目标对象来自新链，不能靠原版 rustc 补齐。

**继续决策：** 评估 trait 推导、借用/drop 两项小规模迁移实验。若必须把 rustc 全局运行时一起搬入，应重划数据契约和语义闭包，而不是继续增加语法数量。

## M2：类型、内存、布局和 ABI

**依赖：** M1；可以在 M1 的接口稳定后先开展测试向量和目标 ABI 调研。

**工作：** 整数宽度、浮点、指针/引用、数组/slice、结构体/enum；常量/静态数据；地址计算、Load/Store、调用效果和内存汇合；布局、直接/间接调用、聚合参数与返回。开放的安全子集同步具备初始化、move、借用和生命周期检查；不把尚未实现检查的引用程序先放行到代码生成。

**出口：** 类型布局与 ABI 对拍、跨函数/独立编译对象的值与内存行为、C FFI 正反向调用通过；支持范围内的对齐、截断/扩展、别名和边界行为正确；效果链 verifier 拒绝非法变换。这里的最小跨编译单元 fixture 不要求提前完成 M4 的 metadata/泛型依赖协议。不把目前 spill 用的 Load/Store 当成通用 Rust 内存支持。

**继续决策：** 在保守内存模型正确前，不引入激进别名假设、Load 消除或跨调用移动。浮点和目标指令能力必须独立记录，不能假设所有 Rust 标量等价于 i64。

## M3：Rust 语义闭包

**依赖：** M1 的核心语义模型与 M2 的必要类型/内存/布局能力；部分算法原型可提前。

**工作：** 泛型替换、trait/关联类型与约束求解、生命周期、move/borrow、初始化和 drop、const 求值、宏卫生和展开、单态实例及其递归；依赖图中必需的内建项逐个落实。

**出口：** 冻结的一组泛型集合、迭代器、trait 调用、常量布局和析构用例正确；借用/类型/初始化反例被拒绝；提前退出及失败路径副作用匹配。需使用小型自包含用例先证明能力，再用 M4 的真实 alloc/std 实现证明库级覆盖，避免把“标准库已可用”作为本阶段的循环前提。

**继续决策：** 建立需求→语义能力→回归证据矩阵。未覆盖的 trait/宏/const 分支显式标记，不以通过几个手写泛型例子宣称完整 Rust 兼容。

## M4：Cargo、metadata 与 sysroot

**依赖：** M2/M3 中对应能力；driver 协议及格式设计可提前进行。

**工作：** Cargo 查询/依赖文件/输出契约、自有 metadata 与 rlib、链接、host 构建脚本和过程宏、core→alloc→std、compiler builtins、目标特性、跨 crate 泛型体和实例身份。格式自有，不宣称与官方 `.rmeta` 私有格式兼容。

**出口：** 干净环境下构建冻结依赖库并完成其功能测试；每个目标 Rust 对象有生产者记录；混合 bootstrap 单列；目标库、host 工具与 C/C++ 依赖分账。不借旧 target/cache 或官方 sysroot 的已编译 Rust 对象伪装 full-native。

**继续决策：** 先验收“目标 Rust 闭包 native”，再验收“host 构建工具也 native”；定义两项不同的覆盖标签。标准 test harness 的 unwind 等依赖未具备时，独立执行 fixture 可以提供局部证据，但不能宣称完整测试矩阵通过。

## M5：真实项目正确性

**依赖：** M4。沿固定 Cargo.lock 和 features 的依赖闭包，从小库到 ripgrep，再到 Cargo；不是先解析顶层源文件。

**工作：** 根据真实阻塞项完成 SIMD/target-feature、atomics、TLS、panic/unwind、过程宏及必要 intrinsic/asm 等支持；处理 Cargo 的 C/C++ 库构建与链接；不修改业务源码来绕过缺失语义。

**出口：** 原生 ripgrep/Cargo 整仓构建成功；正式功能测试及 CLI stdout/stderr、退出码、输出文件/必要副作用对拍通过；每个目标对象来源可追溯；固定语义/配置没有被悄悄削减。

**继续决策：** 性能差距按热点和代码质量原因分类。成功构建是功能里程碑，尚未证明运行性能、体积和编译速度达标。

## M6：机器码质量与编译性能

**依赖：** M5 的正确性出口；测量基础从 M0 开始存在。

**工作：** 依据 profile 推进内联、标量替换、内存/循环优化、向量化、指令选择、寄存器分配与代码布局；完善实例级流水线、内容寻址缓存；确有证据后再做跨 crate 提前发布/优化摘要。需要 LTO 的产品配置使用自有图/摘要机制，不加载 LLVM bitcode 作为实现替代。

**出口：** 按 [验证协议](validation.md) 分别比较 cold、no-op、局部修改、接口修改、缓存 hit/miss；常规 portable release 和相同约束下各自最佳配置均有独立数据。runtime/体积候选比目标为 ≤1.0，统计不确定标记为证据不足；代表负载逐项报告。编译收益必须重复验证，不能用局部 pass 的倍数替代全构建收益。

**继续决策：** 确认改善确实来自减少工作或关键路径缩短；不把缓存命中数据称为无缓存冷编译加速。跨 crate 调度若引入内存峰值、循环等待或失效错误，回退到上一已验证粒度。

## 排期与资源原则

第一轮是十个工作日的架构验证时间盒，见 [首轮计划](batches/01-foundation.md)，不是完整 Rust 的工期承诺。后续按阶段出口重新估算；用实际语义闭包的迁移成本和差分缺陷数量评估，不用 agent 数量换算交付速度。

初期五个职责流可以并行生产独立工作包，但共享契约和依赖链仍由集成人顺序收敛。模块内的图修改先独占执行，跨函数/实例并行；统一 CPU 和内存预算。当前运行环境的测试与远程资源约定在执行时遵守，不把个人主机名或临时凭证写入通用设计。
