# KFRC 与 LLVM 差距分析（2026-11-10）

本文冻结优化前的 final1 基线复算。新代码、重新编译与测量结果见 [本轮实现报告](implementation.md)。

当前 KFRC 的编译工作量已经接近 LLVM，生成代码的运行效率、代码体积和语言支持范围仍有较大差距。在已编译的四个 crate 上，整进程编译指令数几何平均为 LLVM 的 **1.035 倍**，精确 codegen 窗口为 **1.003 倍**；编译墙钟为 **1.205 倍**。库对象 `.text` 为 **2.965 倍**，13 个负载的配对运行耗时几何平均为 **3.443 倍**。

下一阶段建议优先研究 humantime 的聚合值表示与解析路径、base64 的编码和解码循环，以及内联和符号保留策略。链接产物结构应独立改进。继续减少编译器内部开销仍有价值，但不能用这部分收益替代生成代码的运行性能验收。

**版本与比较范围**

本报告分析前一会话最终验收的 `integrated/final1`，对应已合并的 [PR #7](https://github.com/Shomvel/kimi-fast-rustc/pull/7)，GitHub `main` 为 `b254941179c6f052bc2b732814c61ed299e39a3b`。本次重新核验本地 1,451 个源码和测试输入，全部与冻结指纹一致；合并提交中与该清单对应的 1,055 个非 Markdown 文件也全部一致。核验记录见 [source-verification.json](source-verification.json)。

这次工作重新计算已有真实 E2B 测量并检查当前源码，没有重新编译或新增性能采样。正式结果来自同一沙箱内的串行对照：Rust 1.94.1 / LLVM 21.1.8，AMD EPYC，8 vCPU / 16 GiB，Linux x86-64，O3、16 CGU、MIR opt-level 0、panic=abort、debuginfo=0，以及相同 sysroot。正确性预检开启寄存器分配检查，正式编译成本关闭该检查；两者对象字节一致。

运行驱动和 sysroot 使用共同的 LLVM 产物，驱动对象在各方案间相同。这能比较所测库的后端差异，但不能外推为完整应用、整套依赖或标准库全部由 KFRC 编译的结果。MIR-0 也是特定实验设置，尚缺默认 release 配置下的端到端比较。五个候选库中 regex-syntax 未编译成功，不进入四库及 13 负载的平均值。

**总体数据**

所有比值均为 KFRC / LLVM，低于 1 表示该指标更小。运行耗时取 11 轮交错测量的逐轮配对比值中位数；编译整进程取三轮中位数。

| crate | 库对象 .text：LLVM → KFRC | 代码体积比 | 编译指令比 | 编译墙钟：LLVM → KFRC | 运行耗时比范围 |
|---|---:|---:|---:|---:|---:|
| semver 1.0.28 | 18,515 → 34,148 B | 1.84 | 0.894 | 0.280 → 0.340 s | 1.97–7.58 |
| base64 0.22.1 | 8,648 → 29,651 B | 3.43 | 0.944 | 0.254 → 0.290 s | 4.57–9.84 |
| unicode-segmentation 1.13.3 | 8,398 → 18,618 B | 2.22 | 0.856 | 0.332 → 0.340 s | 1.11–3.59 |
| humantime 2.4.0 | 10,426 → 57,477 B | 5.51 | 1.588 | 0.239 → 0.356 s | 1.10–10.71 |

完整 13 个负载、绝对耗时、内存与阶段占比见 [tables.md](tables.md)。平均值描述本套件，不代表一般 Rust 程序；没有按真实业务频率加权。

**运行性能：额外指令已经得到确认，具体执行路径仍需细分**

| 负载 | 配对耗时比 | 动态指令比 | cycles 比 |
|---|---:|---:|---:|
| humantime duration 解析 | 10.71 | 7.57 | 10.71 |
| base64 encode | 9.84 | 6.39 | 9.76 |
| base64 decode | 8.15 | 6.30 | 8.25 |
| semver requirement 解析 | 7.58 | 6.32 | 7.67 |
| semver version 解析 | 4.12 | 4.07 | 4.25 |
| unicode grapheme 反向遍历 | 3.59 | 3.58 | 3.52 |
| unicode grapheme ASCII 正向遍历 | 1.11 | 1.05 | 1.10 |

动态指令和 cycles 来自单独的全进程 perf 采样，每个方案每个负载一次，计数器运行比例均为 100%。这些计数适合判断数量级和研究方向；不能把它们当作 11 轮计时的置信区间。

semver version 解析和 Unicode 反向遍历的耗时、cycles 与指令增幅接近，首先应减少热路径执行工作量。base64 编码和 duration 解析同时存在更多指令与较低 IPC：前者约为 2.96 对 4.52，后者约为 2.99 对 4.24。额外指令已确认；IPC 差距的具体原因未查明。现有最终版本记录没有足够的分支失误、缓存事件及热点指令采样，不能将差距定量归因于 spill、分支预测、指令缓存或 SIMD。

ASCII 正向遍历接近 LLVM，不代表反向遍历也接近。duration 格式化约 1.10 倍，不代表 duration 解析也接近。优化和验收应保留每个负载的结果，避免平均值掩盖严重退步。

上一轮 base64 `.text` 从 54,307 B 降至 29,651 B，但当前 13 负载相对旧版本的耗时几何平均为 0.99918 倍，整体持平。已有 数组优化报告（原始证据 `array/report.md`） 说明收益集中在构造表的函数，而运行负载使用预构造 engine。因此这轮体积下降尚未改善所测编码和解码循环。

**代码体积：大函数与额外独立函数同时存在**

从最终 `nm -t d` 的十进制符号大小重新统计，并逐库核对 FUNC 字节总和与验收 JSON 一致：

| 函数 | LLVM | KFRC | 观察 |
|---|---:|---:|---|
| humantime `Parser::parse_unit` | 1,093 B | 23,799 B | 单函数大 21.77 倍，增加 22,706 B |
| base64 `internal_encode` | 1,376 B | 6,095 B | 编码函数大 4.43 倍 |
| base64 `Alphabet::try_from` | 217 B | 3,667 B | 大 16.90 倍，尚无证据表明它是 encode 计时热点 |
| semver `Version::from_str` | 917 B | 1,934 B | 大 2.11 倍 |
| Unicode `prev_boundary` | 2,906 B | 1,326 B | 本函数更小，但反向遍历仍慢 3.59 倍 |

`parse_unit` 占 humantime FUNC 字节约 41.9%，其单函数增量占该库 FUNC 总增量约 48.9%，是最集中的体积问题。最终编译 profile 也显示它占 humantime 已计数阶段指令约 42.6%，占 x86 阶段指令约 61.8%。这项同时影响编译工作量和代码体积，适合优先分析；其对 duration 解析运行耗时的具体占比仍需最终版本热点采样确认。

符号按相同 mangled name 对齐、仅去掉 LLVM 数字后缀后，分布如下。符号可能包含同名局部副本或别名，不能把符号数直接当作独立源码函数数。

| crate | 共同符号字节：LLVM → KFRC | 仅 KFRC 有独立符号的字节 | 仅 LLVM 有独立符号的字节 |
|---|---:|---:|---:|
| semver | 18,430 → 22,041 | 10,754 | 585 |
| base64 | 8,648 → 18,788 | 10,237 | 0 |
| unicode-segmentation | 8,358 → 8,390 | 9,697 | 40 |
| humantime | 10,426 → 37,184 | 19,632 | 0 |

Unicode 的共同符号总字节很接近，体积增量主要出现在额外独立符号。humantime 同时有共同函数膨胀和额外独立函数。额外符号可能对应内联、删除、合并或不同函数边界，不能全部标为死代码。`prev_boundary` 的例子也说明，单函数大小比较必须结合完整调用链。

当前内联策略使用最大深度 4、新增节点 2,000、计费调用 32、callee 节点 64 等阈值，小函数优先，并对唯一调用点放宽限制。跨 CGU 的私有符号依赖会限制可内联范围；匿名常量复制默认关闭，源码注明旧实验曾造成体积和热路径退步。参见 [InlineBudget](https://github.com/Shomvel/kimi-fast-rustc/blob/b254941179c6f052bc2b732814c61ed299e39a3b/crates/kfrc-son/src/transforms/ipo/mod.rs#L41) 和 [CguGraphs](https://github.com/Shomvel/kimi-fast-rustc/blob/b254941179c6f052bc2b732814c61ed299e39a3b/crates/rustc_codegen_kfrc/src/lib.rs#L419)。这些是已确认的策略限制；各限制对当前 13 个负载的贡献尚未量化，不应直接全面提高阈值。

聚合值表示也有具体历史证据：未合并的 Return-only 候选曾将 `parse_unit` 从 23,799 B 降至 20,252 B，humantime `.text` 减少 8.52%；但其他负载出现约 4%–16% 的退步，因此暂缓。报告见 returns/FINAL.md（原始证据 `returns/FINAL.md`）。该候选支持继续研究构造器与 Phi 的表示成本，但尚未形成可直接采用的优化。

**产物结构：需要单独验收链接后的程序**

| 指标 | KFRC / LLVM，四库几何平均 | 含义 |
|---|---:|---|
| 库对象 `.text` | 2.965 | 机器码节，包含对齐 |
| FUNC 符号大小之和 | 2.871 | 函数符号统计，别名可能重叠 |
| `.rodata` + `.data.rel.ro` | 4.076 | 常量及带重定位的只读数据 |
| 所有 `.o` 文件大小 | 2.151 | 还包含符号表、重定位与文件结构 |
| `rlib` 文件大小 | 1.293 | 还包含 Rust 元数据与归档结构 |

`rlib` 的差距比 `.text` 小，不能据此推断运行时代码已经接近 LLVM；Rust 元数据会改变整体比例。反过来，库对象 `.text` 大 2.965 倍也不能直接描述成最终可执行文件大 2.965 倍。本套件未保留完整的最终程序节大小、strip 后大小、link map、重定位数量和链接耗时对照，最终可执行文件差距尚未测定。

源码确认了两个产物结构限制。第一，每个目标文件的函数都追加到一个 `.text` 节，按 16 字节对齐；链接器按输入节执行垃圾回收时，无法单独移除同节中的未用函数。第二，常量集中追加到只读数据节；该写出路径没有按常量内容去重或声明可合并字符串节。参见 [object_file.rs](https://github.com/Shomvel/kimi-fast-rustc/blob/b254941179c6f052bc2b732814c61ed299e39a3b/crates/kfrc-x86/src/object_file.rs#L64)。因此，函数分节、数据分节以及符合身份语义的常量合并值得独立实验；收益必须在最终链接产物上实测。

这些数据节包括有效常量、源码路径及诊断相关数据。当前数据不足以把全部额外只读数据归因于 panic 信息，也不足以给出可删除比例。函数分节还可能增加目标文件和链接管理开销，验收需要同时比较最终体积与编译、链接成本。

**编译性能：总工作量接近，墙钟和阶段分布仍不同**

四库精确 codegen 指令比依次为 0.869、0.920、0.717、1.766。三个库已经比 LLVM 少执行编译指令，humantime 仍多约 76.6%。峰值 RSS 分别为 144.6、140.3、134.8、161.3 MiB；LLVM 为 146.9、145.7、142.1、139.1 MiB。内存差距也主要集中在 humantime。

当前后端在 [codegen_crate](https://github.com/Shomvel/kimi-fast-rustc/blob/b254941179c6f052bc2b732814c61ed299e39a3b/crates/rustc_codegen_kfrc/src/lib.rs#L125) 中顺序构建图、顺序遍历 CGU 并生成目标文件。LLVM 编译记录中 user 时间可大于 wall，例如 semver 为 0.470 s 对 0.280 s；KFRC 为 0.293 s 对 0.340 s。这支持并行度是墙钟比较的重要因素，但进程启动、调度和系统时间也包含在墙钟中；尚未用并行度消融量化各项贡献。

| 阶段占已计数阶段指令比例 | semver | base64 | Unicode | humantime |
|---|---:|---:|---:|---:|
| x86 降低与寄存器分配 | 27.0% | 26.2% | 26.0% | 49.3% |
| 内联后优化 | 15.6% | 19.2% | 22.8% | 11.6% |
| 内联 | 15.6% | 11.0% | 13.2% | 7.9% |
| 布局降低 | 13.9% | 8.9% | 11.5% | 12.2% |
| 显式验证阶段 | 11.5% | 11.1% | 10.1% | 8.9% |

这里的 x86 阶段包含调度、指令选择、活跃性分析、分配、边复制及机器指令构造，不能把其全部成本写成寄存器分配成本。当前数据支持先拆解 humantime 的大函数成本；semver 没有同等集中的单函数，其最大函数只占阶段指令约 5.7%。

原验收文字将精确总窗口描述为 current-thread，但原始 JSON 和计数器源码明确使用 `initial_process_threads_and_descendants_user_instructions`，包括开始时已有线程及后续 LLVM 工作线程。本次已核对八份总窗口记录，均成功且没有计数复用。只有阶段插桩是 current-thread。总窗口几何平均重新计算为 1.00313；旧汇总中的 `cg=1.00389` 来自“整进程减 metadata”的近似口径，两者应区分。

“整进程编译指令达到 LLVM 的三分之一”与“后端指令达到三分之一”也应分别设目标。例如 Unicode 的 metadata-only 已约 1.014 G，占 LLVM 完整编译 2.144 G 的 47.3%。保留前端和元数据处理工作量时，单靠后端优化不应承诺该库整进程三倍改善。该比例是独立构建的近似成本参照，并非可直接相减的严格阶段下界。

**支持范围与验证缺口**

| 范围 | 当前结果 | 与 LLVM 的差距 |
|---|---|---|
| semver | corpus、checksum、34 项上游集成测试通过 | 仍有性能和体积差距 |
| base64 | corpus、checksum、13 项集成测试通过 | 上游单测构建受 TLS 限制；LLVM 179 项通过 |
| unicode-segmentation | corpus、checksum、8 项集成测试通过 | 上游单测构建缺 `atomic_xsub`；LLVM 15 项通过 |
| humantime | corpus、checksum 一致 | 测试依赖 rand 使用 u128；LLVM 38 项单测通过 |
| regex-syntax | 当前到达 SIMD/union 值拒绝 | KFRC 没有可比较的运行产物；LLVM 147 项单测通过 |

另外，当前后端明确限定 `x86_64-unknown-linux-gnu` 和 `panic=abort`，拒绝全局汇编；对象写出没有 DWARF 节，适配器返回 `dwarf_object: None`。因此跨平台、panic unwind、调试体验及完整工具链互操作均不能宣称与 LLVM 等价。本次未系统验收 LTO、PGO、增量编译和大型应用依赖图，不给这些能力标记通过。

此前的 824 项单测、三方案各 824 行语义差分，以及真实 unicode-bidi 的 768 行一致结果仍然有效。这些结果覆盖已经执行的范围，不能替代上述未编译成功的上游测试。regex-syntax 的缺失还意味着当前平均值排除了更大的复杂 crate。

**建议的实验顺序与验收标准**

| 顺序 | 工作 | 依据 | 验收标准 |
|---|---|---|---|
| 1 | 冻结最终源码重建两种后端的正式二进制，补齐热点和链接记录 | 已有总量数据可靠，缺最终版本完整热点汇编及链接产物 | 保存对象、链接后反汇编、link map、逐符号样本；记录所有指纹，输出及 checksum 一致 |
| 2 | 分析 humantime 的 `parse_unit`、Result/enum/Phi 表示和相邻解析调用链 | 23.8 KB 单函数，阶段编译指令占 42.6%，duration 解析慢 10.71 倍 | 先区分成功与错误路径，比较动态调用、内存搬运、spill 和指令数；体积、运行、编译分别验收 |
| 3 | 分析 base64 `internal_encode`、decode helper/chunk 的内联、边界检查和字节运算 | 编解码动态指令约 6.3 倍，构造表优化未改善这些负载 | 相同输入按字节计成本，核对 IR 与循环汇编；每次机制改动单独对照，覆盖短输入及错误输入 |
| 4 | 改进内联成本模型和符号可达性，覆盖 semver 与 Unicode 反向遍历 | 额外独立函数较多，固定节点阈值不能表达调用频率和实际机器码成本 | 记录每类拒绝原因；比较最终调用链和所有 13 负载，避免只提高阈值 |
| 5 | 函数/数据分节，检查重复常量与重定位 | 单一输入节限制链接回收，只读数据约 4.08 倍 | 小 API 消费者与完整驱动分别链接，比较 section GC、最终 ELF、strip 大小、链接耗时 |
| 6 | 缩小大图并拆解 x86 编译阶段，再研究 CGU 并行 | humantime x86 占 49.3%；当前 CGU 顺序执行 | 分开记录总指令、单核/多核墙钟、RSS；并行收益不能代替工作量减少 |
| 持续 | 补齐 TLS、atomic_xsub、u128、SIMD/union 的真实语义路径 | 当前支持缺口阻断完整测试及第五个 crate | 对照 LLVM 运行原上游测试，不通过更改输入或回退 LLVM 计为支持 |

以上是实施前的后续实验建议，本报告冻结于优化开始之前。后续实现和新测量单独记录。当前可确认的优先级是先减少热路径额外工作量，处理 humantime 的集中膨胀，再分别验收链接体积与编译并行度。SIMD 支持需要补齐，但当前四库的 3.44 倍平均运行差距尚未证明主要由 SIMD 缺失造成。
